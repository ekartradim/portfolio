Orchestrator and parallel lanes

The orchestrator (Opus) never writes product code. It plans waves from the dependencies in Linear and from which files the lanes would otherwise collide on. Every ticket gets its own lane: a worktree, a branch and a dedicated Claude session.

Lanes run in herdr, a terminal multiplexer for coding agents. They report back to the orchestrator by message, and I can open any lane at any time, take over and finish it by hand.

It's all packaged as the ai-toolkit plugin. It builds on Matt Pocock's skills and Lauren Tan's pstack; the gate and lanes come from my own projects.

  • 26skills from triage to retro; each owns one phase and hands an artifact to the next
  • 3read-only reviewer agents (code, spec, comments), with optional cross-model review via Codex
  • 4hooks: pre-merge gate, dangerous-git blocker, post-compaction anchor, shared command parser
  • 1verdict ledger keyed to SHA and patch-id, so an agent can't “recycle” an old green result
Testing and gates

The gate is my main product

Generating code is cheap; knowing it works is expensive. Agents are stochastic, so I wrap them in a deterministic workflow: hooks on the agent, a local gate before merge, and CI on the pull request. The agent proposes, code decides.

This is the feedback loop the headline is about. The agent sees an error in its context within seconds, and whatever fails never reaches trunk, no matter what the agent remembers.

After every edit, a hook runs lint and only the tests the change touched. The result goes straight back into the agent's context.

On PR-based projects the same steps run in CI with branch protection. In “pr + babysit” mode the agent opens the PR, watches the pipeline and fixes until it's green. In the company marketplace, CI on the PR decides whether a plugin gets in at all.

The merge gate from the EVA platform

Every detail of this gate came from a specific agent failure, and the reason is written down in the code.

skip = failure

Without a database, the Postgres tests skip themselves with exit code 0, so a merge would look verified. The gate turns skips into failures.

<sha>.ok + attestation

A green gate writes a marker for that exact commit and an attestation line the lane posts to the Linear ticket. The marker vouches for a commit, never for an uncommitted working tree.

require_gate_before_merge

A hook blocks merge and push to main without a marker for that SHA. Why: after context compaction an agent forgot the “don't merge” line in a skill and the commit went through. A sentence in a prompt can be forgotten; a hook can't.

smart Band 4

Database tests take 250 of 300 seconds, so they run only when the diff touches the database. The decision is recorded in the marker and the hook recomputes it before merge, fail-closed.

--no-ff

A merge commit has a new SHA the gate never saw. So on push the hook also checks the second parent, the lane head the gate verified.

honest boundary

The code states what the hook won't stop. It guards against a forgotten gate, not a shell determined to bypass it. Deliberate bypass is the job of CI and server-side branch protection.

LLMs are stochastic. Gates are deterministic. A software factory rests on knowing where one ends and the other begins.

Agent sandboxing

Claude Code and Codex in microVMs (Docker Sandboxes) · Bash, Python, Node hooks · September 2026

6 sVM from snapshot
~12 scold box to first answer

Without solid isolation you can't leave a software factory running overnight. Here the isolation is measured, not just configured.
  • Key finding: Claude Code's built-in sandbox wraps only the Bash tool. Only a VM boundary contains the agent as a whole, and managed settings don't reach inside it.
  • A per-sandbox egress allowlist, and secrets inside only as placeholders that a proxy fills in. A verification script fires 10 synthetic attacks at the hooks.
  • Measuring it, I found a hole: the network-policy check answered “allowed” from the global rules, so a project could reach an API it never declared.

Evals and grounding

Measure the skill, not the feeling about it

A skill is code for a model, so it needs tests. And what must be true shouldn't be decided by the model.

Skill-distillery

Evals for skills and prompts. Most companies that share skills don't have this.
synthesise→run→grade→diagnose→revise

Runs and grading happen in isolated subagents, so the grader never sees the source and the model never grades itself. A research agent enriches the rubric once, then it's frozen.

A real run, 6 test cases × 6 dimensions. Iteration 5 hit 97.2; iteration 6 dropped to 80.2. Lesson: keep checkpoints and ship the best iteration, not the last one.

Deep-personality-module

Grounding LLM output where mistakes hurt: claims about a person.

“The LLM only writes prose. What has to be true is owned by deterministic code.”

Nine psychometric instruments (344 items) are scored by code. The report is written in three passes: a plan with an evidence map, sections with citation markers, and a final edit that may not add any new claim.

A lint gate releases the report only if every claim is cited and none rests on a middling score that could be read any way. Otherwise it returns 502 and no report is produced. Crisis situations are detected by code, not the model. 118 tests.

Operating model

The AI-Native SDLC

Code is cheap. What's scarce is quality criteria, gates, domain knowledge and ownership.

We rent the harness and the model; we build the criteria, gates, hook content, evidence, skills and failure memory ourselves. The design is harness-agnostic: Claude Code plans and executes, Codex reviews, and open-source models step in where cost or security decides. Six phases from plan to operations, each gate with a named approver and evidence. “Hoping the agent asks” doesn't count as a gate.
